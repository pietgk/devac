## Review of devac-spec-v2.0

### 1) Feasibility (working vs broken)
- Components marked as “preserved” (two-pass parsing, language router, seed writer) are plausible, but several “working” claims depend on TBD pieces: semantic resolver contract, cross-repo edge computation, and hub lifecycle (init/upgrade/backfill) are not defined. Per-package-per-branch storage (adopted) conflicts with legacy per-file partition flows in sections 6.4/8.4, so incremental update logic is effectively “broken/unwritten” until reconciled. Python parser latency mitigation and C# parser are future-state; classify as not implemented rather than working. Hub registry/cache lifecycle lacks owner and durability plan.

### 2) Architecture (two-phase parsing, boundaries)
- Structural→semantic split is sound, but boundaries blur because semantic resolution, edge mutation, and external_refs updates are unspecified (who writes the resolved parquet? where are branch deltas applied?). Storage tier oscillates between per-package (current) and per-file (older diagrams), creating ambiguity for SeedWriter and delete/rename paths. Cross-branch semantics (branch column without entity_id branch) are OK, but interactions with branch deltas for edges/refs need explicit rules. Hub vs package responsibilities (what is cached centrally vs always read from seeds) are under-specified.

### 3) Implementation phases & dependencies
- Phase 2 (incremental) depends on stable hashing + partition strategy, but delete/rename handling still references per-file partitions—dependency mismatch. Phase 4 (federation) lists cross-repo edges as a deliverable but omits design/compute/invalidation steps, making it a blocking dependency for Phase 5 validation. Parallelization note (Phase 2 & 3 together) assumes router and seed writer already support multi-language; call this out as a prerequisite. Make explicit that Phase 5 requires semantic resolution coverage; otherwise affected-file validation will under-report.

### 4) Performance targets realism
- Single-change <100ms and package write <100ms are optimistic: chokidar debounce + hash read + DuckDB startup + temp→rename fsync likely push cold paths to 200–400ms; warm paths with pooled DuckDB and no Python should hit ~120–200ms. Python subprocess targets (<200ms) need a warm, long-lived parser or RPC; without it expect 250–500ms. Cross-repo query <600ms assumes 3 repos × 6 Parquet files each; with dozens of packages or cold FS cache this will exceed 1s unless you add connection pooling and glob pruning. Repo-level <200ms at 10 packages needs benchmarks with the chosen partition scheme.

### 5) Missing pieces / failure modes
- Atomicity/rollback: Section 6.4 hints at temp+rename, but delete handling in 8.4 still deletes partitions directly—define atomic writes for base/branch files and cleanup of .tmp on restart. Hub/manifest versioning, migrations, and corruption recovery are absent. Cross-repo edge staleness handling (TTL, rebuild triggers, failure when hub unavailable) is not specified. Validation when refs remain unresolved (mark/unmark, surfaced warnings) is missing. Concurrency: lock scope (per package? per repo?), timeout, stale-lock recovery need explicit behavior. Schema evolution of Parquet is mentioned for seeds but not for hub tables. No fallback for DuckDB fatal mode during writes.

### 6) Integration points clarity
- FileWatcher → LanguageRouter → Parser path is defined; Parser → SeedWriter is OK structurally, but SeedWriter → SemanticResolver → updated seeds is vague (who owns merged writes and idempotency?). StorageManager/Central Hub contract is unclear: what data is persisted centrally, when are cross-repo edges recomputed, and how are caches invalidated on package changes? Phase 4 assumes external_refs resolution writes back to seeds, but the write path and branch-delta handling aren’t described. Rename/delete flows need to state whether base vs branch parquet gets is_deleted markers or physical deletion.

### Practical implementation challenges / recommendations
- Reconcile partition strategy everywhere (per-package-per-branch, not per-file); update delete/rename, SeedWriter, and incremental diagrams accordingly. Define a semantic resolver module with explicit inputs/outputs and atomic write steps; document how branch deltas are merged for nodes/edges/refs. Add cold vs warm latency budgets and require Phase-1 benchmarks before locking targets; pool DuckDB connections and keep a warm Python worker to hit targets. Specify hub/manifest schema versioning, migration, corruption recovery, and cache/edge invalidation triggers (watcher events + manual rebuild + optional TTL). Clarify lock scope (per package) and stale-lock recovery. Document failure surfaces: how unresolved refs are flagged, how partial writes are rolled back, and how validation degrades when hub is offline.
