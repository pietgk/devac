## Review of devac-spec v1.0 (2025-12-10)

### Feasibility & component status
- The labeled “working” pieces are only partially production-ready: `StructuralParser` and `SemanticResolver` are TS/JS-only experiments (Babel + ts-morph) and are not wired into the main analyzer-service pipeline; tree-sitter parsers exist but use the legacy `Parser` orchestrator contract, not the new structural/semantic split. `StorageManager` handles batch MERGE writes but has no delete/replace path needed for atomic per-file updates. FileWatcher exists and debounces events, but no integration glue currently connects it to parsers or storage. Calling all of these “working” overstates readiness and hides the integration work still required.

### Architecture (two-phase parsing)
- The two-phase idea is sound, but boundaries are underspecified: Phase 1 currently emits full nodes + relationships for TS/JS only; other languages’ parsers emit relationships immediately (not just structural), so a generic “structural” interface does not yet exist. Phase 2 is implemented only for TS/JS and depends on tsconfig discovery, ts-morph Projects, and existing Neo4j nodes; no semantic resolvers exist for other languages, and the spec doesn’t describe how they will be added or how to unify their outputs. There is no contract for how Phase 1 results are transformed into `StorageManager` inputs (e.g., dedupe, label assignment, IDs) or how semantic results coexist with structural ones (conflict/override rules).

### Implementation phases & dependencies
- Phase ordering assumes LanguageRouter → StructuralParser → StorageManager is trivial, but missing steps include: mapping parser outputs into StorageManager batches; deleting/replacing prior nodes/relationships for a file; and queueing semantic work with backpressure. Phase 2 (tree-sitter) presumes the existing parsers drop into the new router without adapters, yet they currently expect the old analyzer flow. Phase 3 (Python) depends on a keep-alive process and a rewritten parser API that the spec doesn’t define. The mention of “fix 11 TypeScript errors” suggests the codebase is not clean; spec doesn’t state whether builds must pass before rollout or how to gate incremental mode until type errors are cleared.

### Performance targets
- Hitting <100ms end-to-end per change is unlikely with the current pieces: FileWatcher defaults to 500ms debounce; `StructuralParser` reads from disk, parses with Babel, and writes via Neo4j network round-trips (StorageManager batches), which alone can exceed 100–200ms for non-trivial files. Semantic batches are explicitly 2–5s and require Neo4j queries plus tsconfig discovery; that makes the <200ms “graph update” target feasible only for Phase 1 structural writes and only if Neo4j latency is very low. Python <100ms is unrealistic without a proven keep-alive parser and cache; SQL is disabled; ts-morph startup cost will dominate for cold semantic queues.

### Missing pieces & failure modes
- No plan for error handling, retries, or backpressure when Neo4j is slow or unavailable; queue persistence is absent, so crashes lose pending semantic work. No rollback/compensation path for “delete then insert” failures—partial deletes could leave holes. Rename/move events are not described (FileWatcher provides only path + type); deduping and idempotency rules for repeated events are unspecified. There is no strategy for versioning or marking stale semantic relationships when structural data changes. Spec does not address testing strategy (unit vs. integration with Neo4j) or observability beyond logs.

### Integration points
- FileWatcher → LanguageRouter → Parser → StorageManager is not fully defined: expected message shape, threading/async model, and transactional wrapper are missing. There is no adapter layer from LanguageRouter outputs to `StructuralParser`/tree-sitter parsers to ensure a consistent `StructuralParseResult`. SemanticResolver is not wired into this chain (who enqueues, when, and with what dependency info?). Atomic update semantics require a delete+insert transaction per file, but StorageManager currently only MERGEs; the spec should prescribe the Cypher shape and how to avoid race conditions with concurrent events.

### Practical challenges to address
- Define a common parser contract (structural output) and adapters for existing tree-sitter parsers. Add an atomic “replace file” operation (delete prior File/Node + relationships, then insert) with retries and metrics. Specify queueing/backpressure (max queue, drop/merge policy) and semantic invalidation rules. Reconcile debounce targets with the <200ms SLA, and budget for Neo4j RTT. Clarify rollout gating on a clean `tsc --noEmit` and how to disable incremental mode if semantic errors spike.
